This reference records approved product direction, implementation progress, and historical context. Approval does not itself mean that behavior is implemented or deployed. Each decision below identifies shipped work where verified; implementation on `main` and production deployment remain separate claims.

## Administrative simplification — Issue #325 (approved 2026-10-29)

**Approved direction; delivered portions are identified below.** [#325](https://github.com/ehuerta6/cappy-hub/issues/325) records the maintainer's confirmed decisions. These decisions set the target for the Event, Task, Points, Warning, and lifecycle contracts and supersede the earlier Cancel/Archive mirror direction in #29. Domain references describe current repository behavior and distinguish accepted direction where work remains. GitHub Issues and PRs retain implementation dependencies, delivery status, and verification history.

#### Purpose and principles

Make Cappy Hub easier to administer: **CRUD First**, **Safe by Default**, **Connected Operations**, **Minimal Restrictions**, and **Simple UX, Reliable Backend**. Authorized users can manage administrative records and correct history. Important deletions are reversible. Changes reconcile genuinely dependent data automatically. Keep restrictions supported by product scope, authorization or integrity; reuse existing architecture and patterns with MVP-level UX simplicity and finished-product reliability.

#### Events and participation Points

- Authorized managers have full Event CRUD, including historical corrections and signup corrections after an Event finishes. Normal Officer self-signup permissions remain time/state limited. Correcting schedules preserves signups; current schedule determines Upcoming/Happening/Past rather than permanent processing state.
- User-facing **Delete + Restore** replaces Cancel and Archive. Delete excludes the Event from active operations while preserving recovery relationships, signups and audit history. Every Event-linked Point transaction, including manual awards, stops contributing to active totals. Restore reconciles eligible records and credit without restoring awards intentionally removed beforehand.
- Automatically reconcile participation after schedule, duration, roster and eligible Time Slot changes. Descriptive changes do not require unnecessary recalculation. Preserve slot bounds/capacity, valid selections and historical relationships; do not silently migrate independent records.
- Participation earns **exactly 1 point per eligible hour**, including eligible fractional slot durations and excluding gaps. Task Points remain a separate fixed-value model. Verify historical configured/snapshotted rates against the database before removing rate-related schema; do not erase historical evidence or assume legacy rates.
- **Implemented for #328 in PR #343 (repository; production deployment separate):** New participation uses 1/hour; schedule/duration changes reconcile automatic credit and mechanically suspend it before a corrected future end. Historical rate schema and snapshots remain. An Admin may confirm one removed award as verified premature, with a required verification reason; the old removed transaction and audit remain intact, and replacement credit is eligible once after the corrected end. Unknown or deliberate removals stay excluded. When an automatic amount was directly edited, or an active legacy award lacks the newer basis metadata, a relevant schedule/duration correction recalculates it from the Event source and records before/after evidence. Missing metadata does not block a valid correction or imply an original schedule; reconciliation establishes only the current basis. Descriptive edits leave amounts unchanged. Ordinary historical Event roster corrections are implemented in #329/#350; historical Volunteer Time Slot assignment corrections are implemented for each confirmed signup, retaining its canonical Event signup and reconciling only that Officer's eligible slot participation.
- **Accepted in #402:** New Event participation uses 2 Points/hour for Volunteers and 1 Point/hour for Attendees, while historical Event awards and fixed Task award values retain their stored behavior. An Officer chooses one signup type; Time Slot signup remains Volunteer. Event completion awards from the recorded signup without an attendance check. #402 also accepts Admin-created exactly −1 Point deductions linked optionally to one Event or Task, negative-only edits, automatic Warnings for groups of three active deductions, a three-active-Warning cap, and explicit manual/automatic origin handling. Deleting one linked deduction removes its complete automatic Warning group while retaining the other deductions; deleting an automatic Warning removes its linked group, and manual Warnings never change Points. At the cap, deductions remain recorded without creating a fourth Warning. The full behavior and constraints are in the active #402 Issue and [Points](points.md), [Warnings](warnings.md), and [Events](events.md) contracts; accepted direction does not imply merge or deployment.
- **Event Delete/Restore (#330) implemented on `main` by [PR #361](https://github.com/ehuerta6/cappy-hub/pull/361); production rollout is separate:** Single-occurrence Event Delete/Restore suspends active Event-linked manual, correction, and participation transactions from totals. Restore only reactivates those mechanically suspended rows and reconciles eligible automatic participation. Legacy cancelled and archived rows are not backfilled or relabeled; old archive Point activity and cancellation semantics remain intact. Calendar mutations continue through the existing direct integration with visible failure feedback; the broader recovery path was later implemented by [#334 / PR #364](https://github.com/ehuerta6/cappy-hub/pull/364). Recurrence-scoped Event and Task Delete/Restore was later implemented on `main` by [#333 / PR #363](https://github.com/ehuerta6/cappy-hub/pull/363); production rollout is separate.
- **Implemented in #327 (repository; production deployment separate):** Manual Points are independent signed credit, with a required reason and optional Event reference. They neither replace nor block automatic participation. Preserve transaction audit history and automatic award uniqueness; retries and concurrent reconciliation must not duplicate awards.
- **Event 53 regression:** the Admin reports that premature awards were manually removed after processing before the actual Event date. The corrected Event retains its five signups and must grant legitimate participation after its actual end. Preserve removed premature awards as history. This is a general schedule-correction regression, not permission for a production repair or an ID-specific rule. Distinguish removed invalid premature awards from deliberate suppression of otherwise legitimate credit; do not globally reactivate removed transactions.
- Preserve occurrence/following-occurrence scopes and existing recurrence semantics where appropriate. Explicit scoped recovery must not restore independently removed occurrences or alter unrelated overrides, assignments or signups. Stable IDs, request idempotency, series revision checks and atomic scope authorization remain essential.
- **Implemented for #333:** Event and Task Delete/Restore support explicit occurrence, following, and series scopes. Restore is limited to the still-deleted members of the selected Delete batch. Stable occurrence identities and relationships remain; affected Points use the established suspension and reconciler functions. Every affected row is authorized, series revisions serialize mutations, and exact retries share the existing recurrence request-key namespace. The lifecycle operations do not change the schedule definition or recreate occurrences.
- **Google Calendar recovery (#334) implemented on `main` by [PR #364](https://github.com/ehuerta6/cappy-hub/pull/364); production rollout is separate:** Eligible creation and edits, scoped occurrence changes, Delete and Restore synchronize with the one-way Google Calendar mirror after the Cappy Hub write commits. Per-occurrence failures remain visible to authorized Event managers in the Events list and Event detail, with a direct retry action that loads current canonical Event state. A failed recurring scope records only its failed occurrences. Retrying uses stable Google IDs and existing conditional upsert/remove operations, so it converges current state without duplicating items or restoring a deleted Event. Server-side credentials and the safe Event payload remain unchanged; no queue or new service was added.

#### Tasks

**Historical corrections (#331), single-occurrence Task Delete/Restore (#332), and recurrence-scoped Task Delete/Restore (#333) are implemented in the repository; production deployment is separate.**

Use the same CRUD and Delete/Restore experience wherever appropriate. Authorized managers can correct completed Tasks, fixed Point values, due dates and assignments. Automatically reconcile dependent Task awards. A relevant fixed Point value change recalculates automatic Task awards from the Task value, including an amount directly edited earlier, and records meaningful before/after evidence. Descriptive edits do not trigger recalculation. Independent manual Points and corrections are never overwritten, and intentional removals are not restored by recalculation. Delete suspends associated awards while preserving Task/assignment/completion history; Restore reconciles eligible awards. Preserve existing Task-specific manager completion permissions and after-due-date America/Denver eligibility, recurrence scopes, independent assignments and contextual Event links. A linked Event change alone does not change Task awards.

#### Warnings

**Implemented in #335 (repository; production deployment separate):** Admins directly create effective Warnings and correct current/historical reasons with before/after audits, without new leadership votes or Dashboard decision prompts. Legacy statuses, approvals and Void history remain unchanged.

**Implemented for #336 in the repository (production deployment separate):** Admins Delete and Restore Warnings using a separate reversible lifecycle marker, while historical Void records retain their original meaning. Delete removes an item from active totals; Restore preserves its prior status and Void history. Three active Warnings still trigger Admin review without automatic deactivation. The everyday legacy approval/review UI is removed; historical approvals, decisions, assignments, statuses and audit evidence remain stored. Delete, Restore, migration, and unrelated edits do not promote legacy rejected or pending Warnings.

#### Catalogs, permissions and consistent UX

**Catalog CRUD (#337) is implemented in the repository; production deployment is separate.** Existing Event Types, Positions, Branches and reusable Event locations support recoverable removal. Existing configuration stays in its owning workflow; no catalog module or historical rate-schema removal is introduced.

Provide authorized CRUD for existing manageable catalogs, including Event Types, Positions, Branches and relevant existing configuration. Referenced values remain recoverable and historically readable without broken relationships. Preserve stable system identifiers, required Position protections and permissions. Do not invent catalog modules.

Admins have global management authority within existing product boundaries; Leads/Managers act within authorized scope; Officers retain authorized personal operations. Keep trusted server/database authorization, RLS and essential integrity rules. Preserve Officer identity, deactivation/reactivation and last-Admin safeguards. This decision does not expand any role through a display name or relationship.

Use consistent Delete confirmations explaining consequences, discoverable Deleted views and Restore actions where appropriate, and clear errors and recovery paths. Preserve meaningful audit history and recoverable data. Avoid exposing lifecycle implementation fields unnecessarily. The Dashboard and internal Calendar derive updated state from the existing domains; they do not acquire independent workflows.

Volunteer Time Slots remain active and unchanged. #### Confirmed automatic Point editing behavior — Option C (2026-10-30)

Direct Point transaction editing remains available for CRUD. Automatic Event participation and Task awards are derived from their source records. A relevant source change replaces a directly edited automatic amount with the source-derived value and records meaningful before/after audit evidence; unrelated descriptive edits do not trigger recalculation. Independent manual Points and corrections remain separate and are never overwritten. Existing protections for intentional removals, historical provenance, eligibility, authorization and audit history remain in force. No edit-protection flag, override, approval workflow or blocking rule is introduced for direct edits.

#### Compatibility gates

Historical Event-rate verification remains an evidence gate before removing historical rate schema; it is not a pending choice about the 1-point/hour rule. [PR #343](https://github.com/ehuerta6/cappy-hub/pull/343) assessed migration and legacy handling with synthetic fixtures and retained historical rate columns and snapshots. Do not infer historical intent from ambiguous removal/lifecycle data. Production historical-data access, deployment, or repair requires its own authorization. Development and tests use synthetic data only.

Period rankings include active Officers with active Points attributed to that period; inactive Officers do not appear in the ranking. ### Google Calendar Event mirror — Issue #29

**Current integration present in repository; production activation is tracked separately.** Cappy Hub is authoritative and the private CIC Google Calendar is a one-way mirror. The integration uses stable Event-derived Google IDs and direct server-side upsert/remove calls after Cappy Hub mutations. Initial activation and server-side write access remain operational concerns. The payload contains Event name, America/Denver schedule, location, general description and protected Cappy Hub link; it excludes signups, attendees, internal notes, Points, audit data and Tasks. Google-side edits never change Cappy Hub; sharing remains CIC's responsibility. Signup/withdrawal does not synchronize. The accepted simplification above replaces the older Cancel/Archive user-facing contract; [#334 / PR #364](https://github.com/ehuerta6/cappy-hub/pull/364) implemented a discoverable recovery path for synchronization failures.
