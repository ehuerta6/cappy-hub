# Recurrence and record lifecycles

## Recurrence and materialized occurrences

### Current / shipped

Recurring Events and Tasks are represented by a series definition plus real materialized occurrence rows. Each occurrence has its own stable record ID and workflow state; the series does not replace the individual Events or Tasks. Creation supports daily or weekly schedules, an interval, weekly weekdays where relevant, and an ending count or date, with a read-only date preview. The trusted database independently validates the generated schedule. Recurring Event Time Slot configuration is copied into independently owned slot rows for each new occurrence; slot signups remain occurrence-specific. “This occurrence,” “This and following occurrences,” and “All occurrences” use the existing recurrence scopes for edits and lifecycle actions where supported. A scoped slot edit is applied only when it can preserve independent selections, capacity, Event bounds, and historical Point transactions; otherwise the operation fails atomically with a clear error.

Recurring Event and Task edits offer **This occurrence**, **This and following occurrences**, or **All occurrences**. Event and Task Delete/Restore support these explicit scopes. Restore operates only on occurrences from the same Delete action; independently deleted occurrences stay deleted. Only fields changed in an edit form apply to its selected scope; per-occurrence overrides and independent signups, assignments, completion, awards, and audits are preserved. When a schedule edit creates new Event occurrences without changing Max volunteers, each new occurrence inherits the selected occurrence's capacity; existing occurrence capacities remain unchanged. A single occurrence date edit preserves its original recurrence key. Date or recurrence-definition edits create a replacement schedule segment and remap existing rows without replacing their stable IDs. Removed schedule slots are not silently recreated. No background job re-expands a series.

Each mutation checks authorization for the selected occurrence and every affected row. Recurrence lifecycle changes lock the series and occurrence rows, advance the series revision, and commit row changes, Point reconciliation, audit entries, and request receipts together. A scoped Restore uses the original Delete batch membership and does not regenerate occurrences or restore an independently deleted row. Series revisions reject stale mutations. Request keys make exact retries idempotent; reusing a key with different input or actor is rejected. Event wall-clock times remain in America/Denver across daylight-saving changes; Task due dates are date-only.

## Entity lifecycles and invariants

These are product lifecycle operations, not a promise that every entity supports generic create/read/update/delete. **Planned** entries are accepted future behavior from the cited Issue and are not available on current `main`.

| Entity            | Lifecycle                                                                   | Lifecycle rules                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Officer           | Create / View / Edit / Deactivate / Reactivate                              | Current. No routine hard delete. History and relationships survive inactivity. Application access requires an active Officer.                                                                                                                                                                                                                                                                                                                   |
| Event             | Create / View / Edit / Delete / Restore / Restore historical cancellation   | Current in #330 and #333: authorized managers Delete and Restore one or scoped recurring occurrences within Event scope. All active Event-linked Points are suspended; signups, slots, relationships, occurrence IDs, and audit history remain. Restore reconciles eligible Points without reviving independently removed awards or separately deleted occurrences. Legacy archives and cancellations retain their meaning and recoverability.  |
| Task              | Create / View / Edit / Delete / Restore                                     | Current in #332 and #333: authorized managers Delete and Restore one or scoped recurring Task occurrences within branch scope. Active automatic awards are suspended; assignments, completion, occurrence IDs and history remain intact. Restore reconciles eligible awards without reactivating independently removed awards or separately deleted occurrences. Deleted Tasks have an explicit manager view and stay out of routine workflows. |
| Point transaction | Create / View / Edit amount where authorized / Correction / Logical removal | Current. Totals derive from active transactions. Corrections are separate transactions; removal retains auditable history.                                                                                                                                                                                                                                                                                                                      |
| Warning           | Create / View / Update / Delete / Restore                                   | Admins create effective Warnings, correct current/historical reasons with audit attribution, and reversibly delete/restore. Active totals include approved, non-voided, non-deleted Warnings; three active Warnings still trigger Admin review without automatic deactivation. Officers see their own active effective Warnings. Legacy approval/status and Void history remain preserved.                                                      |
| Catalog value     | Create / View / Rename / Delete / Restore                                   | Current in #344: create, view, rename, and recoverable Delete/Restore for existing Event Types, Branches, custom Positions, and reusable Event locations. Required Positions stay protected; historical references, stable IDs, and audit meanings remain intact.                                                                                                                                                                               |
