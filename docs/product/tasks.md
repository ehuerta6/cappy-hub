# Tasks

## Tasks

### Current / shipped

A Task has a title, description, Task type, one Branch, a due date with an optional due time for reminder scheduling, Point value, and recurrence metadata when applicable. Due dates and optional times are displayed in America/Denver. Branch and Task Type catalog colors appear with their readable names in Task labels and badges. Its assignments are stored in **`task_officer_assignments`**, the canonical assignment relation. One Task can have multiple Officers. Officers can self-assign when the Task is open to assignment; Leads within their Task Branch scope and Admins can assign or remove one or multiple Officers. During creation, an authorized Lead or Admin may select multiple active Officers; their Branch memberships do not restrict assignment. For a recurring Task, the default applies assignments to the first occurrence only, with an explicit option to apply them to all materialized occurrences. The Task and its selected initial assignments are saved atomically.

Tasks may also have zero or more external resource links. Each link has an HTTP(S) URL and a readable common or custom label. These links are contextual references and do not change Task assignment, completion, or Points.

Completion is tracked independently for each Task/Officer assignment. An active Officer may mark their own active assignment complete. For an ordinary Officer, this reports the completion for review by a Lead in scope or an Admin; the assignment remains awaiting approval until approved. An active Lead within the Task's Branch scope or an Admin who marks their own assignment complete is accepted immediately. A Lead in scope or Admin can approve or reject another Officer's pending report, or use **Approve all pending** on the Task detail page when multiple completion reports await review. Rejection clears the report, notifies the Officer in-app, and allows a new submission without retaining a separate rejected state. Leads and Admins can correct or reverse another Officer's assignment completion on any active Task regardless of Branch membership, as a narrow exception (#465).

Only approved completion earns the Task's fixed Point value, and only after its due date has passed in America/Denver. The optional due time changes reminder scheduling only. A scheduled database processor handles eligible Tasks when the application is closed. If a Lead or Admin corrects an Officer's completion after the due date, the corresponding award is reconciled. Reversing an approved completion logically removes the award; completing again reuses the same Task/Officer transaction. Existing completed assignments and historical approval data retain their meaning. Global completion correction does not broaden Task editing, assignment, deletion, or restoration permissions.

Leads within their Task Branch scope and Admins can correct completed or awarded Tasks, including fixed Points, due dates and assignments. Leads remain limited to their Branch scope for Task management, independent of their broader Event scope. A corrected future due date or removed assignment suspends dependent credit; eligibility recovery reuses the same transaction and preserved completion history. Explicit Admin removals and ambiguous legacy removals stay excluded. Routine processing and descriptive edits preserve historical direct amount edits; explicitly correcting the Task fixed value updates its dependent eligible or mechanically suspended awards with before/after audit. Before saving, the edit form shows an informational confirmation when a fixed-value change affects those awards or a later due date of today or after would suspend active awards; other edits save directly ([#345](https://github.com/ehuerta6/cappy-hub/issues/345)). Due-date processing uses each active assignment's current completion state. Historical approval fields or audit entries retained from an older workflow are historical compatibility only; the retired single-assignee projection and legacy completion/approval RPC workflow are not current product behavior.

Tasks may link to zero or more Events for context. Links do not change either record's authorization, workflow, or Point behavior. Existing links remain readable when an Event is cancelled or archived; cancelled and archived Events cannot be newly linked.

The Tasks page offers **All tasks** and **Assigned to me** quick views, which combine with the existing search, status, Branch, and Officer filters. Its separate **Timeframe** filter supports **Current**, **Past**, and **All** within the selected Academic Period. Current contains Tasks due today or later plus overdue Tasks that are not complete; those overdue rows carry an **Overdue** label. Past contains completed Tasks whose due date has passed, keeping finished work out of the active view. All removes the timeframe boundary while retaining the selected Academic Period. Task sorting supports **Most urgent** (due-date order: overdue first, then nearest due date) and **Newest** (creation time descending). Most urgent is date-based in every timeframe, so completed overdue Tasks may appear before later-due unfinished Tasks in All. Leads in scope and Admins can also select an explicit Deleted view. Assignment progress and the current Officer's relationship to each Task are visible in context. The Calendar shows each active Task due date and opens the canonical Task record.

Leads within their Branch scope and Admins can Delete and Restore a Task, including completed and awarded Tasks. Delete hides the Task from active lists, Dashboard action items, and Calendar, and suspends its active automatic Task awards. The Task, assignments, completion, recurrence identity, Points, and audit history remain available. Restore reuses the existing award reconciler with current due-date and completion rules; an award intentionally removed independently is not reactivated. Each action applies to one Task occurrence.

### Accepted behavior under implementation

Under [Issue #469](https://github.com/ehuerta6/cappy-hub/issues/469), Leads and Admins may mark an overdue Task **No longer needed** or restore it to **Needed**, regardless of Branch membership. This closes the Task for active work while preserving every assignment, completion, and Point record; completion remains editable. The change does not complete unfinished assignments or award Points. It is a separate, reversible Task status, with no confirmation step. Active `Current` lists, Dashboard action items, Calendar entries, and due reminders omit closed Tasks; `Past` remains limited to overdue completed Tasks, while `All` retains closed Tasks with a visible outcome badge. A real transition notifies each active assigned Officer, including those who already completed the Task; repeated no-op updates send nothing.
