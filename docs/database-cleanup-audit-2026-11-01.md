# PostgreSQL/Supabase cleanup audit

**Audit date:** 2026-11-01 (America/Ciudad_Juarez)
**Repository head:** `680119752330e4db85b6c8d52c6d23e815befd03`

**Supabase project:** `CappyHub` (`pftevqvcwdwqkkadllja`), PostgreSQL 17.6.1
**Boundary:** Read-only audit. No production rows were changed and no schema, migration, seed, or data edits were made.

## Executive findings

- The Product & Technical Specification says Volunteer Time Slots remain active. Issue [#349](https://github.com/ehuerta6/cappy-hub/issues/349) was closed as **not planned**, not shipped. The stale #353 bullet was corrected before this audit. Production currently has 8 slots across 2 Events, 24 assignments, 15 slot-linked Point transactions, and 10 participation-basis rows. Time Slots are active behavior and must not be considered for removal.
- Production inventory contains 33 application tables: 24 in `public` (all with RLS enabled) and 9 in `private` (not exposed through the configured Data API schema). It also contains 3 views, 87 indexes, 186 constraints, 23 non-internal triggers, 219 functions, 6 installed extensions, and 2 active cron jobs. Raw object counts are not a cleanup target.
- The live migration ledger has 62 versions through `20261031150000_google_calendar_recovery`. The observed Production deployment is `ec7331e` and matches that migration boundary. Current `main` is `6801197` and adds two academic-period migrations (`20261101000000`, `20261102000000`) that are not yet on Production. This is consistent with `main` being ahead of the observed deployment; it is not evidence of out-of-band schema drift. The exact schema-vs-replayed-migration diff was not run.
- The evidence justifies **no safe schema cleanup now**. Active behavior, preserved history, execution privileges, migration compatibility, and limited query-statistics windows prevent removal decisions for the apparent candidates below.

## Reproducible read-only method and limits

1. Refreshed `origin/main`, read `docs/product/design-doc.md` and `docs/product/administrative-simplification.md`, and inspected the relevant application callers, migrations, database tests, upgrade fixtures, and generated types.
2. From the connected Supabase project, used the read-only `list_tables` (verbose), `list_migrations`, `list_extensions`, and Security/Performance Advisor operations. The table row counts below are aggregate counts only; no Officer names, email addresses, or individual production rows were queried or exported.
3. Ran read-only aggregate `SELECT`s over `pg_stat_user_tables`, `pg_stat_user_indexes`, `pg_constraint`, `pg_trigger`, `pg_proc`, `pg_views`, `pg_matviews`, `pg_policies`, `supabase_migrations.schema_migrations`, and `cron.job`. Slot, assignment, linked-Point, and participation-basis counts were aggregate `count(*)` queries only. No `EXPLAIN ANALYZE`, write, reset, repair, seed, backup restore, or migration command was run against Production.
4. Inspected the current Vercel Production deployment metadata for its Git SHA. Deployment readiness does not establish that an exact live schema diff has run.

The Supabase API inventories the live catalog and migration ledger, but this audit did not dump every `pg_get_*def()` body or replay the remote schema into a comparison database. Function-level review below is targeted to the surfaced candidates and active call paths; it is not a claim that all 219 function bodies were individually audited. Backup plan, restore points, and a restore rehearsal were not inspected. PostgreSQL statistics are cumulative counters whose usefulness depends on the interval since reset; a zero scan is not proof that an index is unnecessary.

A reproduction of the compact catalog counts is:

```sql
select
  (select count(*) from pg_class c join pg_namespace n on n.oid=c.relnamespace
   where n.nspname in ('public','private') and c.relkind in ('r','p')) as tables,
  (select count(*) from pg_views where schemaname in ('public','private')) as views,
  (select count(*) from pg_matviews where schemaname in ('public','private')) as materialized_views,
  (select count(*) from pg_indexes where schemaname in ('public','private')) as indexes,
  (select count(*) from pg_constraint c join pg_namespace n on n.oid=c.connamespace
   where n.nspname in ('public','private')) as constraints,
  (select count(*) from pg_trigger t join pg_class c on c.oid=t.tgrelid
   join pg_namespace n on n.oid=c.relnamespace
   where not t.tgisinternal and n.nspname in ('public','private')) as non_internal_triggers,
  (select count(*) from pg_proc p join pg_namespace n on n.oid=p.pronamespace
   where n.nspname in ('public','private')) as functions;
```

### Clean-up buckets

- **Safe cleanup supported by this audit:** none.
- **Requires migration/compatibility transition:** any future change to legacy Task approval fields, warning history/API, or duplicate Event location representation, each after fresh caller, security and historical-preservation evidence.
- **Blocked by workload, product policy or unverified evidence:** any index removal/addition; any presenter/warning/rate/history removal; any schema claim beyond the migration ledger and catalog inventory; backup/restore capability.
- **Keep:** Volunteer Time Slots, Points and their attribution; Presenter history; Warning approvals/state; recurrence and lifecycle/idempotency records; current RPCs, RLS, constraints, triggers, cron jobs and catalog relationships.

## Migration/deployment alignment

The linked Supabase migration ledger contains 62 migrations and ends at `20261031150000_google_calendar_recovery`. Vercel's latest observed Production deployment is Ready at revision `ec7331e69bbbde854600e3170238ce085c9521d6`, which is the `main` revision before current `main` `680119752330e4db85b6c8d52c6d23e815befd03`. Current `main` adds `20261101000000_academic_periods.sql` and `20261102000000_secure_period_views.sql`; neither appears in Production's migration ledger. The configured production workflow applies migrations before deploying the matching app commit, so the observed gap is consistent with the newer `main` release not yet reaching Production. No evidence here calls for migration repair or any manual intervention.

The Supabase catalog inventory and migration ledger were read, and the app revision and migration boundary were checked. A full linked-vs-replayed schema diff was not run, so physical schema alignment beyond those observable signals remains **not verified**. Re-check after the next deployment if this distinction matters to an implementation decision.

## Workflow and comparison notes

| Source / workflow                                       | Comparison                                                                                                                                                                                             | Status and Cappy Hub tradeoff                                                                                                                                                                                                           |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostgreSQL constraints and `ALTER TABLE` behavior       | Keys/checks enforce data invariants; destructive DDL can remove dependent objects and acquire strong locks.                                                                                            | **Already implemented:** Cappy Hub migrations use constraints for integrity and repository guardrails/upgrade fixtures for contract changes. Retain those protections; review locks and dependencies before any cleanup.                |
| Supabase RLS, functions, testing and backups            | Grants and policies both matter; exposed `SECURITY DEFINER` APIs need narrow execution grants and internal checks; database policies should have database tests. Backups are plan/retention dependent. | **Already implemented / unverified:** public tables have RLS and the repo has pgTAP grant/behavior tests. Current backup/restore setup was not inspected. Keep database auth and test boundaries; no dashboard-only fixes.              |
| Admidio member, role and event-registration workflows   | Offers organization role management and event registration.                                                                                                                                            | **Already implemented in narrower form:** Cappy Hub separates Officers, Branch memberships, roles, Event signups and Point records. The audit found no requirement to import a generic module/role framework.                           |
| Hitobito group hierarchy and group-specific role types  | Flexible nested groups and per-group roles support complex organizations.                                                                                                                              | **Not relevant to approved scope:** Cappy Hub's explicit Officer/Admin/Lead rules and Branch overlap are smaller and already documented; a generic hierarchy would add unapproved permission complexity.                                |
| CiviCRM event participants and contact activity history | Separates Event participant records/status from contact identity and preserves related activity history.                                                                                               | **Useful comparison, already covered by existing boundaries:** Cappy Hub separates `event_officers` from Officers and retains Point/audit history. CiviCRM's broader contact/finance model is not a reason to expand this internal app. |
| Galette member and group management                     | Supports member records, groups/managers, filters, and deactivation while retaining history. Event management is an optional plugin.                                                                   | **Useful comparison / not a new feature request:** stable Officer identities, Branch relationships, filtered directories and deactivation/history exist in Cappy Hub. Optional modules/plugins are not justified here.                  |
